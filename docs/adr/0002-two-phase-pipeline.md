# ADR-0002: 两阶段推送管道（预处理 + 定时分发）

**状态：** 已采纳

**日期：** 2026-08-09

**决策者：** 项目作者

---

## 背景

AI 新闻 Bot 的核心流程是：抓取文章 → LLM 摘要 → 推送飞书卡片。

最简单的实现是「抓取即推送」——每个 source 抓取后立即摘要并发送。但这种方式存在以下问题：

1. **无法按用户偏好推送**：不同群聊有不同的推送时间（09:00 / 12:00 / 18:00）、频率（每天/工作日/每周）、厂商订阅偏好。即时推送无法支持这些个性化设置。
2. **LLM 调用时机不灵活**：摘要需要 LLM 调用（耗时+费 token），如果在推送时才发现没有订阅者，则 LLM 调用被浪费。
3. **无法支持「统一时间推送」**：多个 source 的抓取完成时间不同，用户期望在固定时间收到汇总推送。

## 决策

**采用两阶段管道**，将「处理」和「分发」解耦：

```
Phase 1 (05:00 预处理):
  RSS/HTML fetch → LLM summarize → MySQL store (不推送)

Phase 2 (09:00 / 12:00 / 18:00 分发):
  Query MySQL today's articles → 3层过滤 → send Feishu cards
```

- Phase 1 使用 `NewsPushGraph(push_enabled=False)` — 截断流水线到 store 节点
- Phase 2 是纯 SQL 查询 + 内存过滤 + 卡片发送，不经过 LangGraph

三层过滤逻辑（在分发阶段按序执行）：
1. **推送时间**：ChatPreference.push_time 匹配当前 delivery job 时间
2. **推送频率**：`is_today_in_frequency()` 判断今天是否在频率范围内
3. **厂商订阅**：Subscription 表过滤

## 后果

### 正面

- **灵活的用户偏好**：每个群聊可独立设置时间/频率/厂商组合，互不影响
- **LLM 成本可控**：摘要只在 05:00 执行一次，与推送目标数量解耦
- **推送体验一致**：用户在固定时间收到汇总，而非碎片化推送
- **易于调试**：手动触发时可通过 `/admin/trigger-rss`（仅处理）和 `/admin/trigger-push?time=09:00`（仅分发）独立测试两个阶段

### 负面

- **时效性降低**：凌晨抓取的新闻要到早上 9 点才推送，不适合实时新闻场景
- **存储中间态**：文章在 MySQL 中暂存，增加了数据库存储需求（通过 URL hash 去重缓解）
- **调度复杂度**：4 个 APScheduler 定时任务（1 处理 + 3 分发），增加了运维监控面

## 备选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| 即时推送 | 实现简单、新闻时效高 | 不支持个性化、碎片化体验 |
| **两阶段（选用）** | 个性化灵活、成本可控 | 时效降低、多调度任务 |
| 事件驱动（每条文章入队后独立调度） | 最灵活 | 复杂度高、需消息队列 |

## 相关

- `app/main.py`: APScheduler 4 个定时任务配置
- `app/graph/news_push_graph.py`: `build_push_graph(push_enabled=False)` 截断模式
- `app/subscription/handler.py`: `is_today_in_frequency()` 频率判断
